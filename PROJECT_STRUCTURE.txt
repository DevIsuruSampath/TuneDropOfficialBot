================================================================================
                         HOW IT WORKS - REQUEST FLOW
================================================================================

User sends URL/query in Telegram
         |
         v
    HANDLER (url_handler / song_command)
    +-- @rate_limit: 10 requests per 60s per user
    +-- @force_sub: Blocks non-channel-members (if enabled)
    +-- @once_per_message: Deduplicates duplicate updates
    +-- Classifies input: Spotify track? YouTube? Playlist? Search?
    +-- Creates DownloadRequest
    +-- Calls task_registry.start_download()
         |
         v
    TASK REGISTRY (progress.py)
    +-- Creates DownloadTask with status message + Cancel button
    +-- Checks max_concurrent_tasks (global) and max_concurrent_tasks_per_user
    +-- Queues if limits reached, shows position (#1, #2, ...)
    +-- Spawns worker task -> calls download_manager()
    +-- Persists active tasks to MongoDB for crash recovery
         |
         v
    DOWNLOAD MANAGER (downloader.py) -- routes by InputType:
    |
    +-- SINGLE SPOTIFY TRACK:
    |   1. Generate cache key: "spotify:track:{ID}"
    |   2. Check MongoDB cached_songs collection
    |   3. [HIT] -> _send_cached_audio() via Telegram file_id -> DONE
    |   4. [MISS] -> Run spotdl download (subprocess, 1 thread, 320k MP3)
    |   5. Extract YouTube URL from spotdl output -> download cover art
    |   6. Embed cover in MP3 via FFmpeg
    |   7. If spotdl fails -> fallback to yt-dlp with "ytsearch1:{query}"
    |   8. Upload to SONG_CACHE_CHANNEL_ID, store metadata in MongoDB
    |   9. Generate persistent download link
    |   10. Send audio to user with inline keyboard (Download, Share)
    |
    +-- SPOTIFY PLAYLIST:
    |   1. spotdl save -> extract individual track URLs
    |   2. Batch cache check via get_cached_songs_batch()
    |   3. Retrieve cached tracks from cache channel (download by file_id)
    |   4. Download uncached tracks via spotdl batch (10 per chunk)
    |   5. Embed cover art concurrently (3 parallel FFmpeg processes)
    |   6. Retry failed tracks individually (1 retry per track)
    |   7. Cache newly downloaded tracks to cache channel + MongoDB
    |   8. Build ZIP archive -> upload to PRIVATE_CHANNEL_ID
    |   9. Generate web download link -> send completion message
    |
    +-- YOUTUBE TRACK:
    |   1. Cache key: "youtube:{video_id}"
    |   2. [HIT] -> send cached -> [MISS] -> yt-dlp download
    |   3. FFmpeg convert to MP3 (320kbps) + embed cover
    |   4. Cache to Telegram channel + MongoDB
    |   5. Send audio with download link
    |
    +-- YOUTUBE PLAYLIST:
    |   1. yt-dlp extract_flat -> get all entries
    |   2. Batch cache check -> retrieve cached tracks
    |   3. Download uncached concurrently (5 parallel via semaphore)
    |   4. Cache new tracks, build ZIP, upload, send link
    |
    +-- SEARCH (/song <query>):
        1. Resolve query via ytsearch1 -> get YouTube video ID
        2. Check cache with "youtube:{id}" key
        3. [HIT] -> send cached -> [MISS] -> yt-dlp download
        4. Convert, cache, send
         |
         v
    STATUS UPDATES (progress.py -- throttled ~2.5s edits)
    +-- Phase messages: Queued -> Searching -> Checking cache
        -> Downloading -> Converting -> Packaging -> Uploading -> Completed
    +-- Playlist counter: Progress X/Y, Cached: N, Downloaded: M, Failed: F
    +-- FloodWait handling with exponential backoff (max 60s)
    +-- Dedup: skip edit if text unchanged
    +-- Dead message detection: stop edits if message deleted
         |
         v
    WEB DELIVERY (server.py)
    +-- GET /generate/{ref}
    |   -> Resolve persistent ref from MongoDB download_refs
    |   -> Redirect to download page (/download/{token})
    |
    +-- GET /download/{token}
    |   -> Render download.html with file info + ads
    |   -> Download button triggers /file/{token}
    |
    +-- GET /file/{token}
        -> Decode file_id via FileId.decode() (extracts access_hash, dc_id, file_reference)
        -> Create MTProto media session to correct DC
        -> Stream via raw upload.GetFile (1MB chunks, Range support)
        -> Supports up to 4GB files, no Bot API 20MB limit
        -> Content-Disposition attachment + Accept-Ranges headers


================================================================================
                         STARTUP LIFECYCLE
================================================================================

python -m tunedrop
  -> cli.py: main()
     -> runtime.py: start()
        -> asyncio.run(run())

run():
  1. configure_runtime()
     - settings.ensure_directories() -- creates data/, downloads/, logs/
     - settings.validate() -- checks BOT_TOKEN, API_ID, etc.
     - setup_logging() -- file + console handlers
     - Log uvloop availability at startup

  2. init_database()
     - Async connect to MongoDB
     - Create indexes:
       * file_links: token (unique), user_id+created_at, created_at TTL 24h
       * user_files: user_id+created_at, created_at TTL 24h
       * download_refs: ref (unique)
       * active_tasks: task_id (unique), user_id, created_at TTL 24h
       * cached_songs: cache_key (unique)

  3. _cleanup_temp_dirs()
     - Remove orphaned files from temp/, zip/, playlists/ dirs

  4. _acquire_pid_lock()
     - Exclusive file lock on data/bot.pid
     - Prevents multiple bot instances

  5. Launch concurrent tasks:
     - run_bot() -> Pyrogram client connects to Telegram DC
     - run_web_server() -> Uvicorn serves FastAPI on :8080
     - Both run until first completes, then cancel the other

  6. Cleanup on shutdown:
     - close_database() -- close MongoDB connection
     - close_shared_client() -- close httpx client


================================================================================
                         STORAGE ARCHITECTURE
================================================================================

MongoDB Collections                Telegram Channels
---------------------------        ---------------------------
file_links (24h TTL)               PRIVATE_CHANNEL_ID
  token, user_id, file_id           -> ZIP archives (playlists)
  chat_id, message_id               -> Large audio files (>2GB)
  file_name, file_size              -> Uploaded via send_document
  created_at (auto-expire)

user_files (24h TTL)               SONG_CACHE_CHANNEL_ID
  user_id, token, file_name         -> Individual MP3 files
  created_at (auto-expire)          -> Uploaded via send_audio
                                     -> Cached by cache_key
download_refs (persistent)
  ref, payload (JSON blob)          File System
    user_id, chat_id, message_id    -----------
    file_id, file_name, file_size   downloads/temp/    -> Working files
                                    downloads/zip/      -> ZIP archives
cached_songs (persistent)           downloads/playlists/ -> Playlist MP3s
  cache_key (unique)                downloads/songs/    -> Single tracks
  cache_key_type (spotify/youtube)  data/               -> Bot session
  telegram_file_id                  logs/               -> Log files
  cache_message_id (cache channel msg ID for MTProto)
  title, artist, duration
  file_size, thumbnail_file_id
  download_link

users (persistent)
  user_id, stars_paid
  created_at, updated_at

Cache Key Format:
  spotify:track:{spotify_track_id}
  youtube:{youtube_video_id}

================================================================================
                         KEY DATA STRUCTURES
================================================================================

DownloadPhase (StrEnum) -- 10 states:
  QUEUED -> SEARCHING -> CHECKING_CACHE -> DOWNLOADING -> CONVERTING
  -> PACKAGING -> UPLOADING -> COMPLETED (+ FAILED, CANCELLED)

InputType (StrEnum):
  SPOTIFY_TRACK, SPOTIFY_PLAYLIST, YOUTUBE_MUSIC_TRACK,
  YOUTUBE_MUSIC_PLAYLIST, SEARCH, UNKNOWN

DownloadRequest (dataclass):
  user_id, chat_id, source (URL or query), input_type
  Class methods: from_search(), from_input()

DownloadTask (dataclass):
  task_id: str           -- unique token
  user_id: int
  chat_id: int
  request: DownloadRequest
  status_message: Message -- Telegram message edited for progress
  cancel_event: Event     -- set when user cancels
  worker: Task            -- asyncio task reference
  Throttled editing: ~2.5s interval, FloodWait backoff, dedup

SubprocessResult (dataclass):
  recent_lines: tuple     -- last 50 stdout lines
  error_lines: tuple      -- last 20 error lines

Cache key format:
  spotify:track:{ID}  or  youtube:{ID}

AudioMetadata (dataclass):
  title, artist, duration, thumbnail_path

  MusicDownloadManager class (with @timed decorators on key methods):
    DISPATCH:
      __call__() -> routes Spotify/Search vs YouTube by InputType
      _handle_spotify_or_search() -> track vs playlist
      _handle_youtube() -> track vs playlist

    SPOTIFY TRACK:
      _download_spotify_track()
        1. Cache check (generate_cache_key -> song_cache.get_cached_song)
        2. If miss: spotdl subprocess download
        3. Extract YouTube URL from spotdl output -> cover art
        4. Embed cover in MP3 via FFmpeg
        5. Fallback: yt-dlp if spotdl fails
        6. Upload to cache channel -> (cache_msg_id, audio_file_id, thumb_file_id)
        7. Store real cache_msg_id in download ref payload

        9. _deliver_audio() with download link

    SPOTIFY PLAYLIST:
      _download_spotify_playlist()
        1. _get_spotify_playlist_track_urls() via spotdl save (orjson parsing)
        2. Batch cache check (get_cached_songs_batch)
        3. _retrieve_cached_track() from cache channel
        4. spotdl batch download (10 per chunk)
        5. _embed_cover_art_batch() (3 concurrent FFmpeg)
        6. Individual retry for failed tracks
        7. _cache_spotify_tracks() with cache_message_id tracking
        8. build_zip -> upload_zip_to_storage (stores upload.message_id) -> link

    YOUTUBE TRACK:

        1. Cache check with "youtube:{id}" key
        2. _run_ytdlp_download() with progress hooks (aria2c external downloader)

    YOUTUBE PLAYLIST:

        2. Batch cache check per entry
        3. Concurrent download (5 parallel via semaphore)
        4. _cache_new_tracks() with cache_message_id
        5. ZIP -> upload_zip_to_storage (real message_id) -> link

    SUBPROCESS MANAGEMENT:
      _run_subprocess() - Generic async subprocess runner

        - Stalls detected after configurable inactivity timeout
        - Kills process group (parent + children) on cancel/timeout

      _run_ytdlp_download() - yt-dlp with progress hooks, stall detection

================================================================================
                         RATE LIMITING & PROTECTION
================================================================================

Per-user rate limit: 10 requests per 60 seconds
  - Shows cooldown message with seconds remaining
  - Prunes stale entries every 5 minutes

Task queue:
  - Global: max_concurrent_tasks (default: 10)
  - Per-user: max_concurrent_tasks_per_user (default: 1)
  - Queue shows position (#1, #2, ...)
  - Auto-dequeues when capacity frees

Message deduplication:
  - once_per_message: LRUCache of last 500 (chat_id, msg_id) pairs

Force subscription:
  - Optional Telegram channel membership check
  - 5-minute membership cache per user
  - Admins bypass check
  - Cached channel invite link

Progress editing:
  - ~2.5-second minimum interval between edits
  - FloodWait exponential backoff (max 60s)
  - Dedup: skip if text unchanged
  - Dead message: stop edits if message deleted

Web security:
  - Host validation: only serves requests for configured domain
  - Security headers: X-Content-Type-Options, X-Frame-Options, CSP
  - Token validation: alphanumeric only, max 64 chars
  - Suspicious Telegram file_path detection


================================================================================
                         SUBPROCESS MANAGEMENT
================================================================================

spotdl (Spotify downloads):
  - Run as async subprocess with stdout capture
  - 60s timeout for first output, configurable stall timeout
  - Process group kill (parent + children) on cancel/timeout
  - Output parsed for progress: "Downloaded X", "Found N songs"
  - Rate limit messages filtered from UI
  - Batch mode: multiple URLs in single process for efficiency

yt-dlp (YouTube downloads):
  - Runs in thread (sync library) with asyncio.to_thread
  - Progress hooks: throttled 4s updates with %, speed, ETA
  - Stall detection: configurable inactivity timeout
  - Auto-converts to MP3 via FFmpeg after download
  - Cookie support for authenticated YouTube access

FFmpeg (audio processing):
  - Conversion: any format -> MP3 320kbps
  - Dynamic timeout: 6x audio duration + 300s overhead (min 900s)
  - Cover art embedding: FFmpeg maps audio + image streams
  - Validation: ffprobe checks for valid audio stream


================================================================================
                         DONATION SYSTEM
================================================================================

Currency: Telegram Stars (XTR)
Flow:
  1. User sends /donation -> sees preset buttons (50, 100, 250, 500) + custom
  2. User selects amount or types custom value (1-2500)
  3. Bot sends Stars invoice via aiogram send_invoice
  4. Telegram processes payment through Stars
  5. Bot receives UpdateBotPrecheckoutQuery -> approves via Pyrogram raw
  6. On successful_payment -> subscription_service.record_donation()
  7. User receives thank-you message

Storage:
  users collection: {user_id, stars_paid, created_at, updated_at}
  stars_paid incremented on each donation

Admin:
  /admin -> User Info button -> look up user's total donations
  /stats -> shows total donations across all users
